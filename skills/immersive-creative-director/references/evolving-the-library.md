# Immersive Discovery

Use this protocol to learn from a supplied website, video, process artifact, or repeated Filipe feedback without turning every admired surface into doctrine. Enter it when Filipe asks to study, add, merge, correct, supersede, remove, or extract a lesson from a reference. Immersive Creative Director remains the synthesis and mutation owner.

Supplying a source authorizes full read-only inspection and an evidence-backed recommendation. It does not authorize protected-content bypass, form submission, purchase, contact, publication, or unrelated global changes. Explicitly asking to update/add the installed skill authorizes one in-scope transaction after review; critique, comparison, or study alone does not mutate the package.

## 1. Complete the evidence pass

For a website, use the active Codex desktop in-app Browser—not Chrome. Inspect the whole meaningful site before judgment: every finite unique route/template and primary interaction family, including navigation, overlays, galleries, filters, forms, configuration/product, audio/theme, protected states, utility, conversion, and ending states when reachable without bypassing intent. Separate external destinations, duplicate-language routes, generated catalogue records, and non-evidentiary state changes. Record chronology, hierarchy, spacing/scale, imagery/media/sound, motion and input, transition/camera/topology, orientation, page modes, peak, resolution, and production implications. Capture chronological visual evidence for the opening, composition/density changes, every distinct transition or interaction family, internal page modes, peak, utility states, and resolution. State mobile, touch, keyboard, reduced-motion, loading, and performance evidence only when actually observed.

For a video, invoke the installed Watch skill fully. Inspect the complete meaningful visual runtime and retain timestamps plus representative frames for principles, demonstrations, corrections, failures, before/after states, and tool decisions. Exclude commercials, sponsor tutorials, promotions, and irrelevant outros from the captured evidence; resume the inspection immediately after each excluded segment. Inspect a companion site, repository, artifact, or deliverable when it is needed to verify the claimed lesson. Translate another agent, generator, or vendor workflow into the available Codex/OpenAI workflow while keeping the useful process logic—not its branded tooling. A transcript skim, opening sequence, or unverified vendor claim is insufficient.

Capture limitations rather than smoothing them away. For every authorized Add, Merge, or Counterexample that makes a source part of the active corpus, persist the visual evidence inside the skill package. Store chronological frames under `assets/reference-corpus/frames/<visual-id>/`, create a readable overview sheet under `assets/reference-corpus/overviews/`, add every frame and checksum to `assets/reference-corpus/manifest.json`, and link the visual ID to its written evidence record in `visual-reference-manifest.md`. Transient tool output, session memory, live URLs, and prose-only notes are incomplete evidence storage.

If no inspectable source or artifact is supplied, stop at **blocked for evidence**: ask for the missing source, make no mutation, and choose no disposition. Do not call the absent transaction add, merge, counterexample, reject, redundant, or no-change. Those are evidence-backed outcomes available only after the complete pass above.

## 2. Keep four evidence classes separate

**Observation:** what the full source demonstrably did, with scope and limitation.  
**Preference signal:** Filipe’s exact reaction, authority level (hard rule, strong default, hypothesis, or project direction), and underlying desired quality. A liked mechanism remains conditional.  
**Novelty delta:** the specific future concept, rejection, production, approval, orchestration, or quality judgment that would change; the current records that do or do not cover it; non-transferable identity; and what was not observed.  
**Conflict:** tension between the new evidence and active knowledge. Resolve by authority and evidence, not prestige or recency: current explicit project instructions/hard rules, directly observed scoped behavior, corroborated doctrine, failure boundaries, derived requirements, then single-source hypotheses. Prefer a qualified condition or split rule when strong sources disagree.

If no future decision changes, there is no new installed record. One project reaction does not become universal taste; an existing preference must not block honest observation either.

## 3. Choose one disposition

After the complete evidence pass, choose exactly one primary outcome for the transaction:

- **Add:** one genuinely new operational rule with use and rejection conditions.
- **Merge:** corroborate, qualify, or strengthen an existing record; do not create a synonym.
- **Counterexample:** preserve a contradiction, failure, or boundary that improves future rejection without making it positive doctrine.
- **Reject:** record minimal external provenance and why it is redundant; make no installed change.

A source may reveal several observations, but patch only the families materially changed by that one disposition. Reject patches that add adjectives, duplicate a rule under fresh language, elevate palette/type/imagery/signature sequencing into process, privilege prestige, copy a vendor workflow, generalize from a first screen, or lack provenance, limits, conflict handling, and regression targets.

## 4. Mutate narrowly when authorized

For an authorized add, merge, or counterexample, identify the exact canonical owner and stable written and visual records. Each active record needs an ID, operational rule, use condition, rejection boundary, linked visual ID or Filipe decision, authority/evidence class, status, and any supersession link. Corroboration augments the existing record; qualification edits its conditions; a real contradiction may split an overbroad rule. Remove obsolete active wording while preserving provenance. Never duplicate the same instruction across doctrine, motion, production, quality, orchestration, preferences, and evidence.

Record the source/evidence location and exclusions, preference authority, novelty and conflict analysis, disposition/rationale, records and files changed, provenance, regressions, validation result, and reopened installed location. Analysis-only work ends with the proposed disposition and patch; it must never claim installation.

## 5. Prove the transaction

Run only the affected regressions plus a small cross-family control: concept/doctrine changes test originality, reference-copy, vague brief, multi-project, and premature-completion behavior; motion changes test weak effect, path/timeline, transformation, and mobile; production/media changes test media choice, continuity, and build-through-Codex; quality changes test critique, completion, build verification, and whole-site coverage; preference changes require two subject-diverse direction runs; orchestration changes include the supporting-skill transformation route; evolution changes include a redundancy case and a genuinely novel-source transaction.

Broader core/approval changes require the full relevant behavioral set. A reject/no-change disposition still validates that no mutation was warranted, rather than running a ritual full suite. Completion for an installed Add, Merge, or Counterexample requires full inspection, one disposition, captured preference/provenance/limitations, persisted frames, overview sheet, updated `manifest.json`, passing `validate_visual_corpus.py`, passing targeted proof, and reopening the installed artifact to confirm both written and visual records. A source is not installed when its images exist only in the current conversation or session cache.
